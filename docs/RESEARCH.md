# 研究与实现过程

本文记录这个集成从设备识别、协议确认到 Home Assistant 落地的正确路径。内容刻意省略真实账号、设备参数、授权响应、日志和抓包数据。

## 1. 先明确目标和边界

目标不是替换灯具控制盒或放弃原厂生态，而是同时满足：

- Home Assistant 能在局域网内控制开关、亮度和色温；
- 华为智慧生活仍可使用；
- 不刷写固件、不解除原有绑定；
- 在发送任何控制命令前，先用只读请求证明设备、地址和凭据一一对应。

这几个约束把研究方向限定为“复现官方 App 已经在使用的本地协议”。

## 2. 建立可信的设备清单

先在路由器中记录每盏灯的 IP 和 MAC，并通过灯具上下线变化确认物理房间与网络地址的关系。厂商 OUI 只能帮助判断 Wi-Fi 模组来源，不能证明应用层协议。

完成识别后，为每盏灯建立 DHCP 地址保留。固定地址不仅方便配置，也是后续抓取单设备流量、验证多灯映射的基础。

## 3. 确认真正的本地入口

从 Home Assistant 所在网段和手机所在网段分别检查设备可达性，并观察官方 App 控制时的局域网通信。正确入口最终收敛为：

```text
UDP 5686
  └─ CoAP
      ├─ 会话协商
      ├─ 加密状态读取
      └─ 加密服务控制
```

这一步很重要：Wi-Fi 模组厂商、产品品牌和 HA 里已有的同名集成都不能代替端口与报文级证据。

## 4. 三种证据交叉验证

协议复现没有只依赖单一线索，而是把以下证据放在一起：

1. 官方 App 在用户已授权账号下产生的运行日志和网络行为；
2. 官方 App 安装包的静态分析，用于定位会话字段、CoAP 选项和加密流程；
3. 对自有灯具的只读实测，用于验证字段含义和序列变化。

账号授权是在华为官方页面交互式完成的。研究阶段只在本地、权限受限的临时文件中保存每台设备的 `device ID` 与 `authCode`，发布前完全排除这些文件。现在仓库提供经过脱敏的一次性获取工具；OAuth token 只存在于内存中，不显示也不落盘。完整证据链和可重复步骤见[凭据获取与恢复手册](CREDENTIAL_ACQUISITION.md)。

## 5. 先匹配凭据，不先控制

同一账号下可能存在多台设备，拿到多条本地授权记录后，不能按接口返回顺序猜测房间。正确做法是针对每个固定 IP：

1. 使用一条候选记录建立本地会话；
2. 发送只读 `devDataInfo` 请求；
3. 只有能完成解密和 HMAC 验证的记录才算匹配；
4. 记录“IP ↔ 设备唯一标识”的关系；
5. 全部匹配完成后再进入控制验证。

这样不会因为房间名、列表顺序或路由器备注错误而控制错灯。

## 6. 从最小协议客户端开始

第一版只实现四层最小能力：

1. CoAP 编码与解析，包括编号大于 2048 的厂商自定义选项；
2. `.sys/sessMngr` 会话协商；
3. AES-CBC、PKCS#7、HMAC-SHA256 和序列号处理；
4. `devDataInfo` 只读状态解析。

只有状态读取连续稳定后，才加入以下服务写入：

| 能力 | 服务 | 数据字段 |
| --- | --- | --- |
| 开关 | `switch` | `on` |
| 亮度 | `brightness` | `brightness` |
| 色温 | `cct` | `colorTemperature` |

设备状态中的服务数组有时被再次编码成 JSON 字符串，因此解析器需要递归处理嵌套字典、列表和字符串化 JSON，而不能依赖单一响应外形。

## 7. 用可恢复方式验证控制

控制测试遵循固定顺序：

1. 读取并保存原始开关、亮度和色温；
2. 只改变一个属性并立即回读；
3. 再验证组合指令；
4. 测试关灯；
5. 从关闭状态带亮度和色温重新开灯；
6. 恢复原始状态并再次回读。

这一步发现了一个真实时序问题：灯具在收到重复的“开灯”命令后，会短暂重新应用墙壁开关预设，覆盖紧随其后的亮度或色温。

最终修正是：

- 灯已经开启时，不再发送多余的 `switch/on`；
- 从关闭状态开灯且还要设置属性时，先开灯，等待约 250 ms，再发送亮度和色温；
- 每组命令结束后读取设备真实状态，而不是只在 HA 中乐观更新。

## 8. 适配 Home Assistant

协议稳定后才封装 HA 集成：

- `config_flow.py`：用只读状态请求验证 IP 与凭据；
- `client.py`：保持为同步、无 HA 状态的协议客户端；
- `coordinator.py`：把 UDP 工作放到执行器线程，用锁串行化单灯访问，每 15 秒轮询；
- `light.py`：转换 HA 的 1–255 亮度和设备的 1–100%，暴露色温与开关；
- `strings.json` / `translations`：提供中英文配置界面。

会话或网络错误会使客户端对象失效。协调器最多重试一次，并在重试前重新协商会话，因此灯具重启或会话过期后不需要重载整个 HA。

## 9. 多灯部署验证

每盏灯各自拥有配置条目、协调器、会话锁和唯一设备标识。多灯接入时依次执行：

1. 固定 IP；
2. 只读匹配凭据；
3. 通过 HA 配置流程添加；
4. 检查配置条目为 `loaded`；
5. 对照实体注册表、配置条目和原始 IP 状态；
6. 不依赖房间名猜测设备关系。

## 10. 简要记录未采用的方向

早期也核对过现有 Opple 集成、红外/射频遥控、模组厂商协议和替换控制盒方案。这些方向或缺少精确型号证据，或会失去原厂功能，或不能提供状态回读，因此没有作为本项目的主路径。

## 11. 发布前隐私处理

发布目录从源头采用白名单复制，只包含集成源码、通用测试和文档。随后扫描：

- 私网 IPv4 与 MAC 地址；
- OAuth、Bearer、access/refresh token 等字段；
- 设备 ID、authCode 和长十六进制字符串；
- 日志、抓包、APK、压缩包和 Python 缓存；
- Git 提交历史中的敏感内容。

仓库从干净目录初始化，使研究工作区的历史文件不可能随提交进入远端。
